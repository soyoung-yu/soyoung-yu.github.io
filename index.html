기술 스택
Python SQL AWS Bedrock LLM Codex Claude Code Figma
프로젝트 설명

사내 데이터 서비스 이용률이 저조한 문제를 분석하는 과정에서, 서비스 자체의 기능이나 품질보다 직원들의 데이터 활용 경험 부족이 근본 원인이라고 판단했습니다. 이에 데이터를 단순히 제공하는 방식에서 벗어나, 실제 업무에 적용 가능한 인사이트를 전달함으로써 직원들의 데이터 활용 경험을 확대하고자 정기 인사이트 리포트 발행 프로젝트를 기획했습니다.

리포트는 매 회차 서로 다른 비즈니스 주제를 선정하여 외부 시장 데이터와 사내 연구·생산 데이터를 분석하는 방식으로 제작했으며, 비전문가도 쉽게 이해할 수 있도록 차트 설계와 인사이트 해석에 집중했습니다. 또한 단순 분석 결과 나열이 아닌 하나의 스토리라인을 기반으로 구성하여 데이터가 자연스럽게 의사결정으로 연결될 수 있도록 설계했습니다.

총 12회의 리포트를 제작·배포했으며, 배포 후 3일 평균 조회수 100회 이상을 기록했습니다. 추가 데이터 분석 요청은 기존 대비 약 4배, 신규 대시보드 구축 요청은 약 2배 증가하는 성과를 달성했고, 직원들의 데이터 활용 경험 확대와 데이터 기반 의사결정 문화 형성에 기여했습니다.

LLM 기반 Formulation 자동화

기술 스택
Python SQL Claude Code LLM (Bedrock Sonnet)
프로젝트 설명

제형 연구원은 고객사의 개발 의뢰가 접수되면 요구사항과 유사한 기존 처방(백본 처방)을 찾은 후, 이를 기반으로 성분 및 함량을 조정하며 처방 개발을 진행합니다. 그러나 사내에는 수만 건의 처방 데이터가 축적되어 있음에도 불구하고, 원하는 조건에 부합하는 처방을 효율적으로 검색할 수 있는 체계가 부족하여 연구원 개인 또는 동료의 경험과 기억에 의존하는 경우가 많았습니다. 또한 신규 연구원의 경우 적절한 백본 처방을 찾고 고객 요구사항에 맞게 수정하는 과정에서 많은 시간이 소요되는 문제가 존재하였습니다.

이에 사내 처방 데이터와 성분 데이터, 외부 뷰티 플랫폼의 전성분 데이터를 활용하여 연구원의 자연어 요구사항을 기반으로 초기 처방을 자동 생성하는 LLM 기반 Formulation 자동화 로직을 설계하였습니다. LLM을 활용하여 사용자 질의에서 성분, 효능, 제형, 타겟 제품 정보를 추출하고, 내부 처방 통계 및 유사 처방 탐색 결과를 결합하여 처방을 생성하도록 구현하였습니다. 또한 도메인 제약조건을 프롬프트에 반영하여 생성 결과의 실무 활용성을 높였습니다.

이를 통해 연구원의 반복적인 백본 처방 탐색 업무를 지원하고, 신규 연구원의 처방 설계 진입 장벽을 낮출 수 있는 가능성을 확인하였습니다. 또한 내부 데이터를 활용한 LLM 기반 처방 설계 자동화의 실현 가능성을 검증하였습니다.

배경 및 목표

제형 연구원의 처방(Formulation) 연구 효율성을 높이기 위해 자연어 질의를 받아 초기 처방을 생성하는 LLM 기반 자동화 로직을 구현함

데이터 수집 및 전처리
데이터 수집

사내 DB

  • 처방 데이터
    • 약 25,000개 제품의 처방(Formulation) 데이터
    • 제품을 구성하는 원료, 성분, 함량
    • 시스템 DB의 2개의 테이블을 조인하여 활용
  • 성분 데이터
    • 성분에 대한 메타 데이터
    • 성분의 공식명칭, 역할 (용제, 유화제, 점증제 등)
    • 시스템 DB의 1개의 테이블을 활용

외부 구매 데이터 (뷰티 플랫폼)

  • 제품명, 제형 (카테고리)
  • 제품의 전성분 정보
데이터 전처리

사내 DB

  • 제품을 구성하는 원료 정보(A) 테이블과 원료를 구성하는 성분 테이블(B)을 조인

외부 구매 데이터

  • 제품의 전성분 포맷 정규화
분석 방법론
성분명 정규화 및 매핑
  • 외부 제품 전성분과 내부 성분 DB를 연결하기 위한 성분명 정규화 수행
  • Exact Match, Embedding Similarity, LLM 기반 보완을 활용하여 매핑 정확도 향상
LLM 기반 정보 추론 및 보완
  • 사용자 질의에서 성분, 효능, 제형, 타겟 제품 등의 핵심 정보를 추출하여 구조화
  • 자연어 형태의 요구사항을 처방 생성에 활용 가능한 구조화 데이터로 변환
통계 기반 컨텍스트 생성
  • 성분별 사용 빈도 및 함량 분포 산출
  • min, max, median, p25, p75 등의 통계 지표를 생성
  • 유사 처방, 성분 역할 등의 정보와 함께 컨텍스트로 구성되어 LLM 처방 생성 근거로 활용
LLM 프롬프트 엔지니어링 기반 처방 생성
  • 역할(Role), 지시사항(Instruction), 출력 포맷(Output Schema)을 정의한 프롬프트 설계
  • 사용자 요구사항, 성분 통계, 유사 처방 정보를 기반으로 초기 처방(Formulation) 자동 생성
  • 도메인 제약조건을 프롬프트에 반영하여 생성 결과의 실무 활용성 향상
  • 생성 결과에 대한 반복 테스트 및 프롬프트 개선을 통해 생성 품질 고도화
AI Agent 기반 개발 효율화
  • 처방 생성 로직을 단계별로 정의한 기획 문서 작성
  • Agent가 일관된 방식으로 개발할 수 있도록 개발 규칙 및 명세 문서화
  • Agent를 활용하여 코드 구현 및 반복 개선 수행
  • 연구원 피드백을 반영하여 처방 생성 로직 지속 고도화
분석 결과 및 인사이트
초기 처방 설계 자동화 가능성 확인
  • 연구원의 자연어 요구사항만으로 초기 처방 설계가 가능함을 확인
  • 내부 처방 데이터와 LLM을 결합하여 반복적인 벤치마킹 및 백본 처방 탐색 업무를 자동화할 수 있는 가능성 확인
데이터 기반 컨텍스트의 중요성 확인
  • 실제 처방 설계 프로세스를 반영하여 프롬프트를 설계할 경우 처방 생성 품질이 향상됨을 확인
  • 유사 처방, 성분 통계, 타겟 제품 정보 등을 함께 제공할 경우 생성 결과의 품질이 향상됨을 확인
  • LLM 단독 생성보다 내부 데이터를 활용한 컨텍스트 기반 생성 방식이 실무 활용성 측면에서 효과적임을 확인

  • 향후 AI 기반 처방 생성 시스템의 지식 베이스로 활용 가능
AI 기반 Formulation Assistant 구축

  • 신규 연구원의 학습 지원 및 처방 설계 생산성 향상 도구로 활용 가능

글로벌 연구소 법인 KPI 측정을 위한 SSOT 설계

기술 스택
Python SQL LLM (Claude) Codex
프로젝트 설명

연구소 각 법인은 매월 의뢰, 확정, 초도, 매출 KPI를 수작업으로 집계하여 중앙 부서(GCC)에 제출하고 있었습니다. GCC에서 KPI 정의 및 산출 기준을 제시하고 있었으나, 실제 집계 과정은 각 법인의 엑셀 기반 수작업에 의존하고 있어 휴먼 에러 발생 가능성이 높았으며, KPI 기준 해석의 차이로 인해 법인 간 성과 비교의 신뢰성이 낮은 상태였습니다.

이에 시스템 DB를 기반으로 KPI 집계 과정을 원천부터 검증하고, 법인별 KPI 산출 로직과 예외 처리 기준을 분석하였습니다. 그 결과 동일 KPI에 대해서도 법인마다 서로 다른 집계 기준과 예외 규칙이 적용되고 있음을 확인하였으며, 관계 부서 및 현업 연구소와 협의를 통해 KPI 정의를 재정립하고 글로벌 공통 KPI 체계를 수립하였습니다. 최종적으로 표준화된 KPI 로직을 기반으로 SSOT(Single Source of Truth)를 구축하고 KPI 집계 자동화 체계를 구현하였습니다.

배경 및 목표

기존 각 법인이 수작업으로 관리하던 KPI 집계 체계를 시스템 DB 기반의 자동화 방식으로 전환하고, 법인별로 상이했던 KPI 산정 기준을 표준화하여 글로벌 연구소의 성과를 동일 기준으로 측정할 수 있는 SSOT(Single Source of Truth)를 구축하고자 함.

  • 엑셀 형태의 수작업 보고 자료 확보

  • 확정/초도 : 자재 마스터 테이블을 기반으로 KPI 집계용 데이터 마트 구축
  • 매출 : 관계 부서와 협업하여 법인별 자재 매출 데이터 마트 확보

  • KPI 정의, 집계 기준, 제외 조건 등의 차이를 분석하여 표준 KPI 산출 기준 수립

법인별 KPI 정의 및 집계 기준 차이 발견

동일한 KPI 명칭을 사용하고 있었으나, 실제 집계 기준은 법인별로 상이하게 운영되고 있음을 확인

  • 확정일 기준 차이
    • 일부 법인 : BOM 상태값 1110으로 변경된 시점
    • 그외 법인 : BOM 상태값 1111로 변경된 시점
  • 의뢰/개발 법인 활용 기준 차이
    • 일부 법인 : 의뢰법인 기준으로 의뢰 수 집계
    • 그외 법인 : 개발법인 기준으로 의뢰 수 집계
법인별 예외 처리 로직 존재 확인
  • 일부 법인은 현지 운영 환경을 반영하여 별도의 제외 조건을 적용하고 있음을 발견
  • 예) 특정 고객사의 과도한 의뢰 건을 집계 대상에서 제외
  • 법인의 주관적 판단에 따라 KPI 수치가 달라질 수 있음을 확인

KPI 정의 재정립 및 표준화

관계 부서와 논의하여 KPI가 측정하고자 하는 성과의 정의를 기준으로 글로벌 공통 KPI 체계를 재검토

KPI 기준 재검토 결과

  • 확정 KPI 기준 표준화
    • 기존 확정 KPI는 BOM 상태값 1111 시점을 기준으로 운영되고 있었음
    • 그러나 KPI의 목적을 고려할 때, 실제 처방 확정 시점인 BOM 상태값 1110이 더 적합하다고 판단
    • 이에 확정 KPI 기준을 BOM 상태값 1110 기준으로 통일함
  • 의뢰 KPI 기준 표준화
    • 기존 의뢰 KPI는 의뢰 법인을 기준으로 운영되고 있었음
    • 그러나 KPI의 목적이 연구소의 성과 측정에 있는 만큼, 실제 개발을 수행한 연구소를 기준으로 평가하는 것이 적절하다고 판단
    • 이에 의뢰 KPI 집계 기준을 개발 법인 기준으로 통일함
예외 처리 기준 정비
  • KPI 목적에 부합하는 예외 조건은 유지하고, 공정성을 저해하는 예외 조건은 제거
